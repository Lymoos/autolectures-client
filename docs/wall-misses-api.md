# Пропущенные пары — что нужно на сервере

Клиент уже шлёт эти данные. Ниже точное описание запроса и того, что с ним
делать. Задача — копить пропуски, чтобы потом собрать общую сводку по группе
(«стена» лучших прогульщиков).

## Что считается пропуском

Клиент сам решает и шлёт событие один раз на занятие. Условия: с конца пары
прошло 10 минут, отметки по QR не было, внутри трансляции пробыли **меньше
часа**. Ноль минут (вообще не заходил) тоже попадает сюда.

Пары, где отметка прошла, и пары, где просидели больше часа без отметки, не
шлются вовсе — это не пропуск.

Повтор исключён на клиенте (в занятии ставится флаг), но сервер всё равно должен
защищаться от дублей: клиент могли переустановить, а расписание синхронизируется
между устройствами.

## Эндпоинт

### POST /api/v1/wall/miss

Заголовок `Authorization: Bearer <access_token>` — обычная авторизация, как у
`/api/v1/sync/*`.

```json
{
  "lesson_id": "sch:6f2a91c0de",
  "group": "ИВБО-21-23",
  "subject": "ЛК Управление информационно-технологическими проектами",
  "start": "2026-09-08T18:00:00",
  "end": "2026-09-08T19:30:00",
  "seconds_inside": 420,
  "marked": false
}
```

- `lesson_id` — идентификатор занятия у клиента. Он стабилен для конкретной пары
  конкретной группы (считается из времени начала и названия), поэтому годится
  как ключ для защиты от дублей.
- `seconds_inside` — сколько секунд клиент реально пробыл в трансляции.
- `marked` — всегда `false` в текущем сценарии, поле оставлено на будущее.

Ответ: `200 OK`, тело клиент не читает. Ошибку клиент только пишет в журнал и
не повторяет — терять единичные события не страшно.

## Что хранить

```
Miss
  id
  user_id            — из токена
  telegram_username  — на момент события (может быть пустым)
  group              — код группы из запроса
  lesson_id          — ключ занятия
  subject            — название пары
  start, end         — время пары
  seconds_inside     — сколько просидел
  created_at
```

Уникальность: `(user_id, lesson_id)`. Повторный POST с тем же ключом — не
ошибка: обновите запись или молча верните `200`.

**Telegram-ник берите на сервере**, из привязки аккаунта (`/api/v1/telegram/*`),
а не из запроса — клиент его не шлёт и слать не будет. Если привязки нет,
сохраняйте пустое значение: имя можно подтянуть позже, при построении сводки, по
`user_id`.

## Что понадобится дальше (можно сразу заложить)

Сводка по группе — её будет показывать клиент или бот:

### GET /api/v1/wall?group=ИВБО-21-23&period=month

```json
{
  "group": "ИВБО-21-23",
  "period": "2026-09",
  "top": [
    { "telegram": "@Lymoos", "user_id": 12, "misses": 7, "minutes_inside": 34 },
    { "telegram": "@someone", "user_id": 31, "misses": 3, "minutes_inside": 120 }
  ]
}
```

Сортировка по числу пропусков, при равенстве — по меньшему времени внутри.
Периоды: неделя, месяц, семестр — на твоё усмотрение, клиент подстроится.

Кого показывать: только участников той же группы, что и запрашивающий. Чужие
группы отдавать не нужно.

## О приватности — стоит решить заранее

Данные личные: видно, кто и сколько прогулял. Прежде чем показывать сводку всей
группе, лучше предусмотреть хотя бы одно из:

- согласие: пользователь включает участие в «стене» в настройках, иначе его
  события копятся, но в общей выдаче он не показывается (поле `public bool` у
  пользователя);
- или анонимизация: в сводке только количество, без имён, а имя видит лишь сам
  пользователь.

Клиент к любому варианту готов — он шлёт только сам факт пропуска. Скажи, какой
выберешь, и я добавлю переключатель в настройки.

## Чего делать не нужно

- Обратной отправки клиенту ничего не требуется: он не показывает «стену» до
  того, как появится `GET /api/v1/wall`.
- Уведомлений в Telegram по каждому пропуску не надо — иначе бот превратится в
  зануду. Если захочется, лучше одна сводка в конце недели.
